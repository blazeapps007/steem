# HF24 — Witness-Based SVM Bridge Oracle

**Hardfork:** `STEEM_HARDFORK_0_24` · **Blockchain version:** `0.24.0` · **Gate symbol:** `STEEM_BRIDGE_ORACLE_HARDFORK`

**In short:** In real time, an off-chain oracle bot running as a scheduled witness polls the SVM's
`pending_withdrawals` feed every few minutes and, for each finalized burn it hasn't seen before, signs
and broadcasts a new `bridge_submit_operation` attesting to that withdrawal (SVM `tx_hash`, recipient,
amount, symbol). HF24 adds three consensus changes that act on those attestations: (1) a new signed
operation `bridge_submit_operation` plus two chain-emitted virtual ops (`bridge_release_operation`,
`bridge_oracle_expired_operation`), and new `bridge_oracle_object` / `bridge_processed_object` state
objects; (2) an **evaluator** that counts confirmations per distinct `(tx_hash, payload)` from
currently-scheduled witnesses and, on reaching the threshold (1 on testnet, 17-of-21 on mainnet),
**earmarks** the amount by debiting the key-nullified `svm.bank` reserve and scheduling payout 22 blocks
later; and (3) a **per-block sweep** that, at that maturity block, credits the recipient
(supply-neutral — a transfer from `svm.bank`, never a mint), records a terminal replay guard so the same
`tx_hash` can never be released twice, and expires any candidate that never reached quorum. Every
decision is a deterministic, hardfork-gated function of chain state, and `validate_invariants` is
extended to account for in-flight earmarked funds so total supply stays balanced.

<br>
This document describes **only** the bridge-oracle code addition — the operations, objects, evaluator,
per-block sweep, APIs, and the off-chain oracle bot. It picks up **after** a withdrawal has been
finalized on the SVM (the oracle has caught the burn/withdraw transaction) and follows it all the way
to the asset landing in the recipient's Steem account.

---

## 1. What HF24 adds

A **permissionless, supply-neutral** path to move STEEM and SBD from the **Steem Virtual Machine (SVM)**
to Steem. Instead of a bridge committee with its own keys, HF24 reuses the existing scheduled witnesses:
each witness **observes** a finalized SVM withdrawal and **attests** to it on Steem via a new operation.
The chain reaches consensus on each individual withdrawal and, once the confirmation threshold is met,
**releases** the asset from a pre-funded, key-nullified reserve account (`svm.bank`) to the recipient.

Two hard guarantees:

- **Supply-neutral** — the release is an internal transfer `svm.bank → recipient`; `current_supply` /
  `current_sbd_supply` never change. No mint anywhere in the design.
- **Deterministic & replay-safe** — every consensus decision is a pure function of chain state, and each
  SVM `tx_hash` can be released **at most once** (enforced by a terminal on-chain guard object).

## 2. End-to-end lifecycle (SVM burn → Steem credit)

```
        SVM (CometBFT chain "steemvm")                         STEEM (this codebase, HF24)
 ┌───────────────────────────────────┐
 │ user burns wrapped STEEM/SBD;      │
 │ steembridge module records a       │
 │ PENDING withdrawal:                │
 │   id, burn_tx_hash, created_at,    │
 │   destination_steem_account,       │
 │   amount_millisteem, status        │
 └───────────────┬───────────────────┘
                 │ REST: GET /steemvm/steembridge/v1/pending_withdrawals
                 ▼
        ┌────────────────────┐   for each NEW withdrawal (cursor = SVM `id`)
        │  oracle.js (bot)   │──────────────────────────────────────────────┐
        │  runs as a witness │                                              │
        └────────────────────┘                                              ▼
                                              signs & broadcasts  bridge_submit_operation (op tag 47)
                                                                            │
                                                                            ▼
                                              ┌──────────────────────────────────────────────┐
                                              │ bridge_submit_evaluator::do_apply             │
                                              │  · publisher must be a scheduled witness       │
                                              │  · anti-equivocation, dedup, MAX_CANDIDATES    │
                                              │  · +1 confirmation on the (tx_hash,payload)    │
                                              │    candidate object                            │
                                              │  · at MIN_CONFIRMATIONS → EARMARK:             │
                                              │      debit svm.bank, set release_block = C+22  │
                                              └───────────────────────┬──────────────────────┘
                                                                      │ every block, C+22 later
                                                                      ▼
                                              ┌──────────────────────────────────────────────┐
                                              │ database::update_bridge_oracle() (per block)   │
                                              │  · RELEASE: credit recipient,                  │
                                              │    emit bridge_release_operation (vop),        │
                                              │    write bridge_processed_object (replay guard) │
                                              │  · EXPIRE: candidates past deadline w/o quorum  │
                                              │    emit bridge_oracle_expired_operation (vop)   │
                                              └──────────────────────────────────────────────┘
```

**State machine of a single candidate `(tx_hash, payload_hash)`:**

```
PENDING ──(reaches MIN_CONFIRMATIONS at block C)──► EARMARKED (svm.bank debited, release_block=C+22)
   │                                                     │
   │ (deadline reached, never earmarked)                 │ (block C+22 sweep)
   ▼                                                     ▼
EXPIRED (vop, no funds moved, retryable)             RELEASED (recipient credited, vop, replay guard) ── TERMINAL
```

## 3. Submission type — `bridge_submit_operation` (op tag `47`)

The only **signed** operation HF24 introduces. Requires the **active** authority of `publisher`.

### 3.1 Structs

```cpp
// libraries/protocol/include/steem/protocol/steem_operations.hpp

struct bridge_request {                 // one finalized SVM withdrawal
   fc::sha256        tx_hash;           // SVM burn tx hash (32 bytes)
   uint32_t          block_num = 0;     // SVM block number (feed: created_at)
   time_point_sec    block_time;        // attest time / SVM block time
   account_name_type recipient;         // destination Steem account
   share_type        amount;            // integer, smallest unit of `symbol`
   asset_symbol_type symbol;            // STEEM_SYMBOL or SBD_SYMBOL
};

struct bridge_submit_operation : public base_operation {
   account_name_type          publisher;   // the submitting witness
   vector< bridge_request >   requests;     // batch; may be empty (heartbeat)

   void validate() const;
   void get_required_active_authorities( flat_set<account_name_type>& a ) const { a.insert(publisher); }
};
```

- `FC_REFLECT( bridge_request, (tx_hash)(block_num)(block_time)(recipient)(amount)(symbol) )`
- `FC_REFLECT( bridge_submit_operation, (publisher)(requests) )`
- **Operation variant position:** inserted immediately **before** the virtual-operation marker in
  [operations.hpp](libraries/protocol/include/steem/protocol/operations.hpp) → **tag 47** in a build
  without SMT (default). The tag is append-only; nothing before it was reordered.

### 3.2 `validate()` rules

- `validate_account_name(publisher)`; empty `requests` is allowed.
- Each request: `validate_account_name(recipient)`, `amount > 0`, and `symbol ∈ {STEEM_SYMBOL, SBD_SYMBOL}`.

### 3.3 Binary serialization (what the signer emits)

`bridge_submit` is unknown to stock JS libraries, so the bot serializes it by hand. Body layout after
the op tag varint (`47`):

| Field | Encoding |
|-------|----------|
| `publisher` | varint length + UTF-8 bytes |
| `requests.size()` | LEB128 varint |
| per request → `tx_hash` | 32 raw bytes |
| `block_num` | uint32 LE |
| `block_time` | uint32 LE (epoch seconds) |
| `recipient` | varint length + UTF-8 bytes |
| `amount` | int64 LE |
| `symbol` | 8-byte legacy asset symbol (`03 'T''E''S''T''S' 00 00` on testnet; `TBD` for SBD) |

Digest signed = `sha256( CHAIN_ID_bytes ‖ tx_serialization )`, secp256k1 **graphene-canonical**
(recovery id + 31, canonical-form retry loop).

### 3.4 JSON form (for `broadcast_transaction` / block explorers)

```json
{"type":"bridge_submit_operation","value":{
  "publisher":"initminer",
  "requests":[{
    "tx_hash":"defe53f84ec3e7f3b23c1e37a86eecd8efdbddd40d52855842154e34fc0ed065",
    "block_num":151330,
    "block_time":"2026-07-28T09:16:08",
    "recipient":"blaze.apps",
    "amount":1000000,
    "symbol":{"nai":"@@000000021","decimals":3}
  }]
}}
```

`@@000000021` = STEEM/TESTS (`asset_num` 3200000035), `@@000000013` = SBD/TBD (`asset_num` 3200000003).

## 5. State objects & indexes

```cpp
// libraries/chain/include/steem/chain/steem_objects.hpp

class bridge_oracle_object {            // one per distinct (tx_hash, payload_hash) candidate
   id_type            id;
   fc::sha256         tx_hash;
   fc::sha256         payload_hash;     // sha256(pack(block_num,block_time,recipient,amount,symbol))
   uint32_t           block_num;
   time_point_sec     block_time;
   account_name_type  recipient;
   share_type         amount;
   asset_symbol_type  symbol;
   t_flat_map<account_name_type,uint16_t> confirmations;  // used as a SET (value unused)
   uint32_t           confirmation_count;                 // == confirmations.size()
   uint32_t           created_block;
   uint32_t           expires_block;    // created_block + LIFETIME_BLOCKS
   uint32_t           consensus_block;  // 0 = not yet at quorum; else block C (funds earmarked)
   uint32_t           release_block;    // 0 until consensus; else C + MATURITY_BLOCKS
};

class bridge_processed_object {         // terminal replay guard, written ONLY on release
   id_type       id;
   fc::sha256    tx_hash;
   uint32_t      processed_block;
};
```

> **Note on `confirmations`:** it is a `t_flat_map<…,uint16_t>` used as a set. fc's allocator-aware
> `flat_map` pack/`to_variant` path is the proven one for shared-memory containers; `flat_set` is not
> variadic over the allocator, and fc has no `to_variant(char)`, so `uint16_t` is the mapped value.

**Indexes** (`multi_index_container`):

| Index | Key | Purpose |
|-------|-----|---------|
| `by_id` | `id` | primary |
| `by_payload` | `(tx_hash, payload_hash)` unique | O(log n) candidate lookup |
| `by_tx_hash` | `(tx_hash, id)` | enumerate/count candidates for a tx, equivocation & consensus scan, purge losers |
| `by_expiration` | `(expires_block, id)` | expiry sweep |
| `by_release_block` | `(release_block, id)` | release sweep (`release_block==0` sorts first, skipped via `lower_bound(1)`) |

`bridge_processed_index`: `by_id` + unique `by_processed_tx_hash`.

Registered in [index.cpp](libraries/chain/index.cpp) via `STEEM_ADD_CORE_INDEX` (also registers the MIRA
delegate). Object type ids are **appended** to `enum object_type` in
[steem_object_types.hpp](libraries/chain/include/steem/chain/steem_object_types.hpp) — never inserted
mid-enum (the id is the persisted slot).

## 6. Protocol constants (config.hpp)

```cpp
// libraries/protocol/include/steem/protocol/config.hpp
#ifdef IS_TEST_NET
#  define STEEM_BRIDGE_ORACLE_MIN_CONFIRMATIONS  1                                 // single-witness release
#else
#  define STEEM_BRIDGE_ORACLE_MIN_CONFIRMATIONS  STEEM_HARDFORK_REQUIRED_WITNESSES // 17 of 21 scheduled
#endif
#define STEEM_BRIDGE_ORACLE_LIFETIME_BLOCKS    100800   // ~3.5 days @3s (pre-consensus deadline)
#define STEEM_BRIDGE_ORACLE_MAX_CANDIDATES     3        // distinct payloads per tx_hash (anti-spam)
#define STEEM_BRIDGE_ORACLE_MATURITY_BLOCKS    22       // release at consensus_block + 22
#define STEEM_BRIDGE_BANK_ACCOUNT             "svm.bank"
```

- **Testnet** confirms in a **single** consensus (1 witness); **mainnet** needs **17 of 21** scheduled
  witnesses — Steem's DPoS supermajority (`STEEM_HARDFORK_REQUIRED_WITNESSES`).
- **Maturity delay** of 22 blocks (~66 s) between consensus block `C` and payout ensures `C` is
  effectively irreversible before funds leave the reserve (a fork can't double-release).

## 7. Hardfork gate

```cpp
// libraries/protocol/hardfork.d/0_24.hf
#define STEEM_BRIDGE_ORACLE_HARDFORK STEEM_HARDFORK_0_24   // uniform on both networks

// libraries/protocol/hardfork.d/0_25.hf  (parked — SMT relocated here, not shipped)
#define STEEM_SMT_HARDFORK STEEM_HARDFORK_0_25
```

- All new consensus behavior is gated on `STEEM_BRIDGE_ORACLE_HARDFORK`. Before the HF block the
  operation is rejected and the sweep is inert.
- On the HF block, `apply_hardfork(STEEM_HARDFORK_0_24)` sets up `svm.bank`: nulls its owner/active/
  posting authorities if the account exists (mainnet), or creates it key-nullified (testnet). See §8.
- SMT was never activated on mainnet; HF24 is reassigned to the bridge and SMT is parked at HF25.
- `hardfork.hpp` is generated by `cat-parts` at build time — never hand-edited.

## 8. `svm.bank` reserve account

A **key-nullified** account (owner/active/posting cleared like `steem.dao` / `STEEM_TREASURY_ACCOUNT`)
holding both STEEM and SBD. No private key can ever spend it — **only bridge consensus** releases from it.

- Operational invariant: `balance(svm.bank) == total STEEM/SBD locked on the SVM`.
- Funding is operational (out of band); the code never seeds its balance.
- Set up in the `apply_hardfork` case at the HF block. On testnet the HF creates it; on mainnet the HF
  only nulls the keys of the pre-existing account.

## 9. Evaluator — `bridge_submit_evaluator::do_apply`

`libraries/chain/steem_evaluator.cpp` (~L3342). Registered in `initialize_evaluators()`.

All rejections below are **silent skips** (op stays valid, no state change) — so a batch mixing new and
stale requests still applies the new ones. The only hard `FC_ASSERT`s are the HF gate, malformed input,
and the reserve-funds check at consensus.

1. `FC_ASSERT( has_hardfork(STEEM_BRIDGE_ORACLE_HARDFORK) )`.
2. Determine whether `publisher` is in the current round's `current_shuffled_witnesses`. If not
   scheduled, its confirmations don't count → skip its requests.
3. For each `req`:
   - `bridge_processed_object` exists for `req.tx_hash` → **skip** (already released).
   - Scan candidates via `by_tx_hash`: any with `consensus_block != 0` → **skip** (winner locked); if
     `publisher` already appears in any candidate's `confirmations` → **skip** (anti-equivocation: one
     witness attests a given `tx_hash` at most once, across all payloads).
   - Compute `payload_hash`; look up `by_payload(tx_hash, payload_hash)`:
     - not found → if candidate count ≥ `MAX_CANDIDATES` skip; else **create** the candidate with
       `confirmations={publisher}`, `confirmation_count=1`, `created_block=now`,
       `expires_block=now+LIFETIME_BLOCKS`.
     - found → insert `publisher`, `++confirmation_count`.
   - If `confirmation_count >= MIN_CONFIRMATIONS` → **consensus + earmark** at block `C=now`:
     ```cpp
     asset amt( bo.amount, bo.symbol );
     FC_ASSERT( _db.get_balance(STEEM_BRIDGE_BANK_ACCOUNT, bo.symbol) >= amt,
                "svm.bank reserve insufficient for bridge release" );  // per-tx assert; never halts chain
     _db.adjust_balance( STEEM_BRIDGE_BANK_ACCOUNT, -amt );            // debit reserve; held in-flight. NO adjust_supply.
     bo.consensus_block = C;
     bo.release_block   = C + STEEM_BRIDGE_ORACLE_MATURITY_BLOCKS;
     // purge losing (non-earmarked) candidates for this tx_hash; keep bo.
     ```
     No recipient credit and no replay guard yet — the earmarked winner stays in state until the sweep
     releases it at `C+22`.

## 10. Per-block sweep — `database::update_bridge_oracle()`

`libraries/chain/database.cpp` (defined ~L3625, called ~L3431). Runs every block from `_apply_block`,
just after `update_median_feed()` / `update_virtual_supply()`. Inert unless
`has_hardfork(STEEM_BRIDGE_ORACLE_HARDFORK)`.

- **(1) RELEASE** — walk `by_release_block` from `lower_bound(1)` while `release_block <= now`:
  `adjust_balance(recipient, +amount)` (no `adjust_supply`), push `bridge_release_operation`, write
  `bridge_processed_object` (terminal guard), `remove` the candidate. The credit can never fail because
  funds were reserved at consensus.
- **(2) EXPIRE** — walk `by_expiration` while `expires_block <= now`: skip earmarked winners
  (`consensus_block != 0`), else push `bridge_oracle_expired_operation` and `remove` (no guard written →
  `tx_hash` remains retryable).

Both passes are O(k) via block-ordered indexes (touch only what is due this block).

## 11. Supply accounting — `validate_invariants()`

Between `C` and `C+22` an earmarked amount is debited from `svm.bank` but not yet credited (held
in-flight by the object, exactly like escrow / convert_request funds). `validate_invariants()` adds
earmarked candidates back so totals balance against `current_supply` / `current_sbd_supply`:

```cpp
for( each bridge_oracle_object bo )
   if( bo.consensus_block != 0 )                       // pre-consensus ones are still in svm.bank's balance
      total_supply/total_sbd += asset(bo.amount, bo.symbol);
```

Nothing is double-counted; STEEM and SBD are both handled.

## 13. Oracle bot — `SteemOracle/oracle.js`

Off-chain witness bot: polls the SVM REST feed, and for each **new** withdrawal signs & broadcasts a
`bridge_submit_operation` as a scheduled witness. Hand-rolls serialization/signing with
`@noble/secp256k1` + `bs58` only (op tag 47 is unknown to stock libs).

### 13.1 Commands

```bash
node oracle.js run          # poll every POLL_INTERVAL_MS and attest (default; 3-minute loop)
node oracle.js once         # single poll+attest pass, then exit
node oracle.js create-account <name> <owner> <active> <posting> <memo>   # create a recipient
node oracle.js fund-bank <amountTESTS>                                    # witness → svm.bank reserve
node oracle.js change-keys [<owner> <active> <posting> <memo>]            # rotate the witness account keys
                                                                         #   (omit all 4 → auto-generate a fresh key, prints WIF)
```

### 13.2 Config (env, with defaults)

| Var | Default | Meaning |
|-----|---------|---------|
| `NODE_URL` | `http://127.0.0.1:8090` | Steem node for RPC/broadcast |
| `FEED_URL` | `https://reststeemvmd.steemscanner.com/steemvm/steembridge/v1/pending_withdrawals?pagination.limit=100` | SVM pending-withdrawals feed |
| `WITNESS` | `initminer` | `publisher` (must be a scheduled witness) |
| `WIF` | testnet init key | **active** private key of `WITNESS` (rotate off the default in production) |
| `CHAIN_ID` | testnet chain id | signing digest prefix |
| `POLL_INTERVAL_MS` | `180000` (3 min) | poll cadence |

State is persisted in `SteemOracle/oracle-state.json` (`last_id` cursor + seen `tx_hash` set) so the bot
never double-attests across restarts.

### 13.3 Output — printed bridge submission data

Each poll prints the parsed SVM withdrawal and the exact op being broadcast:

```
[poll 2026-07-28 09:16:08] SVM pending_withdrawals=1 (last_id=-1)
  ┌ bridge_submit  id=0  publisher=initminer
  │  svm_burn_tx : defe53f84ec3e7f3b23c1e37a86eecd8efdbddd40d52855842154e34fc0ed065
  │  svm_block   : 151330   sender: steem107662cdhfe760n2lk9yhsv8fdve3pkzhlmtsvu
  │  recipient   : blaze.apps
  │  amount      : 1000000 (1000.000 STEEM/TESTS)
  │  op          : {"publisher":"initminer","requests":[{ … }]}
  └ broadcast OK → witness attested (awaiting on-chain consensus)
```

### 13.4 Operator quick-start

```bash
# 1. (once) ensure the recipient exists and the reserve is funded
node oracle.js create-account blaze.apps <owner> <active> <posting> <memo>
node oracle.js fund-bank 100000

# 2. (production) rotate the witness off the default key, then run with the new WIF
node oracle.js change-keys                       # prints a fresh WIF
WIF=<new-wif> node oracle.js run                 # 3-minute real sync loop

# 3. verify a specific tx on-chain
curl -s $NODE_URL -d '{"jsonrpc":"2.0","method":"database_api.find_bridge_oracle","params":{"tx_hash":"<hash>"},"id":1}'
# after C+22 blocks:
curl -s $NODE_URL -d '{"jsonrpc":"2.0","method":"database_api.find_bridge_processed","params":{"tx_hash":"<hash>"},"id":1}'
```

> The witness **block-signing** key is separate from the **account** key. `change-keys` only rotates the
> account authorities used to *sign submissions*; block production is unaffected.

## 15. Security properties

- **No griefing.** Competing payloads are independent; a Byzantine witness can only spawn a *competing*
  candidate (bounded by `MAX_CANDIDATES`), never block or corrupt the honest majority's payload. Expiry
  is non-terminal (retryable).
- **Supply conserved.** Releases only move balance out of the pre-funded reserve; supply counters never
  change, and `validate_invariants` accounts for in-flight earmarked funds.
- **Reversibility-safe.** The 22-block maturation makes the consensus block effectively irreversible
  before payout; chainbase undo cleanly reverts a reorg inside the window.
- **Liveness / safety bound (mainnet).** A release needs ≥17 of 21 scheduled witnesses; a *bogus*
  release would require ≥17 colluding — far beyond the standard <⅓ fault assumption.
- **Reserve dependency.** A short `svm.bank` at consensus rejects that single confirming tx (per-tx,
  never a chain halt) — surfacing as a stuck bridge-in, never lost or created money.
